SpatialBench on Spark

GeoFunctions on Apache Spark 4.3 against DuckDB 2.0 spatial, SpatialBench queries Q1 to Q10.

Data: SpatialBench v0.1.0, SF1 (6M trips) and SF10 (60M trips) · Machine: 16 cores, 128 GB RAM, local NVMe · Spark local[*], 64 GB driver · Times: warm median seconds · Source: results/sf1-sf10.jsonl

Summary

  • Spark with GeoFunctions is faster than DuckDB on Q8, Q9 and Q10 at all tested scales.
  • On Q9 (building overlap), Spark is 221 times faster at SF1. DuckDB compares every building with every building.
  • On Q10 (trips in each zone), Spark is 22 times faster at SF1.
  • On Q1, Q2, Q3, Q6 and Q7, Spark is 1.1 to 2 times slower. Spark has a fixed cost of about 60 ms for each query job.
  • On Q4 and Q5, Spark is 3 to 4 times slower. The cause is Spark itself: a top-k sort and a collect_list over all trips.
  • When the data is sorted by QR cell (QR-prepared), Spark answers Q1, Q3 and Q6 in 0.05 to 0.27 s.

The QR grid

A spatial join without an index compares every row of one table with every row of the other table. The QR grid gives Spark an equality key, so it can use a hash join.

cell
A square of the grid. The size of the square is the cell size, in the units of the coordinates.
q, r
The column and row of a cell: q = floor(x / cell), r = floor(y / cell).
qr
One 64-bit key for a cell: (q << 32) | (r & 0xFFFFFFFF).
envelope
The smallest rectangle that holds a geometry.
dist
A distance that makes the envelope larger before the cells are found. Use it for distance joins.
canonical cell
The cell that holds the lower-left corner of the overlap of two envelopes. QR_INTERSECT keeps a pair only in this cell, so the join returns each pair one time.

How each query is written

The SQL is not a copy of the SpatialBench SQL. Each query uses the plan that is fastest on Spark. The results are the same.

Q1 and Q3: distance from a constant geometry

The query uses ST_DWITHIN. The constant geometry is parsed one time for each task. Pairs with envelopes that are far apart are rejected before the exact test.

Q2: points in a constant polygon

The county polygon comes from a scalar subquery. ST_INTERSECTS keeps the last parsed geometries, so the polygon is parsed one time, not 6 million times. Time at SF1 went from 66 s to 0.170 s.

Q4: points in zones, top 1000 trips

The 1000 points are broadcast. The zones are streamed. A shuffle of the zone table took 1.9 to 44 s. The broadcast join takes 0.503 s at SF1.

Q5: convex hull for each customer and month

The query counts the groups first. Then it collects the points only for groups with more than 5 trips. The limit is Spark collect_list, not the geometry.

Q6: trips in zones near Sedona

Point-in-polygon join with 1 cell for each point. The geometry cache keeps 4 polygons, because each trip meets 2 or 3 counties in turn.

Q7: detour ratio

The length of a line with two points is the distance between the points. The query uses ST_DISTANCE, not ST_LENGTH(ST_LINE(...)). This is 3 times faster.

Q8: pickups near buildings

Each building is put in all cells that its envelope touches after the envelope is made larger by 0.0045°. Each point is in 1 cell. The buildings are broadcast.

Q9: overlapping buildings

QR self-join at 0.05° cells. QR_INTERSECT and id1 < id2 keep each pair one time. Spark: 0.178 s. DuckDB: 39.4 s.

Q10: trips in each zone

Spark gives each row its own copy of a binary value. With one row for each (zone, point) pair, Spark copied about 1 TB of polygon data at SF1. ST_WITHIN_MASK tests all points of a zone in one call. Time at SF1 went from 20 s to 3.731 s.

QR preparation

QR preparation writes the data one time, sorted by QR cell. A query that needs a small area then reads only the row groups for its cells.

  • The trip table gets the column t_pickup_qr and is sorted by it.
  • Each zone polygon is cut into one piece for each cell (qr_geom). The piece keeps its envelope.

Preparation at 1° cells takes about 46 s at SF1 and 65 s at SF10. The preparation also makes DuckDB faster. Q5, Q7, Q8, Q9 and Q10 do not use the prepared layout, because they do not select a small area.

A list of cells helps only when the cells are near each other. For Q4, the 1000 points are spread over the world. A list of 700 cells was slower than a read of all rows.

Cell size

  • For a broadcast join, the cell size has a small effect.
  • For a point-in-polygon join, use a cell near the size of the small geometry plus dist.
  • For QR preparation, use a cell near the size of the query area.
  • Do not use a cell so small that a large polygon goes into thousands of cells. At 0.5°, the shuffle join for Q4 took 44 s.

Procedures

Run the benchmark

  1. Install the Python packages: pip install huggingface-hub duckdb pyspark==4.3.0
  2. Build the jar for Spark 4.3: mvn -P spark-4.3 clean package
  3. Install the Python package from the repository root: pip install .
  4. Set the jar path: JAR=$(ls -S target/geofunctions-*.jar | head -1)
  5. Download the data: hf download apache-sedona/spatialbench --repo-type dataset --include "v0.1.0/sf1/*" --local-dir data
  6. Run Spark: python benchmarks/spatialbench/bench.py spark "$JAR" data/v0.1.0/sf1 sf1
  7. Run DuckDB: python benchmarks/spatialbench/bench.py duckdb - data/v0.1.0/sf1 sf1
  8. Compare the result field of each output line.

Run only some queries

  1. Add the argument queries=Q9,Q10 after the number of runs.

Run the QR-prepared benchmark

  1. Prepare the data: python benchmarks/spatialbench/prepare.py "$JAR" data/v0.1.0/sf1 prepared/sf1_c1 1
  2. Run Spark: python benchmarks/spatialbench/bench_qr.py spark "$JAR" prepared/sf1_c1 1 sf1
  3. Run DuckDB: python benchmarks/spatialbench/bench_qr.py duckdb - prepared/sf1_c1 1 sf1

Make this page again

  1. Write the results to benchmarks/spatialbench/results/sf1-sf10.jsonl.
  2. Run python benchmarks/spatialbench/make_report.py.

Limits

  • Spark needs about 2.5 s to start a session. DuckDB needs 0.08 s.
  • Spark has a fixed cost of about 60 ms for each query job.
  • Spark reads the Parquet geometry column about 3 times slower than DuckDB.
  • All tests used one machine. No test used a cluster.
  • The spark-4.3 build uses the Spark 4.0 builds of the spark-shp and FileGDB readers. These readers are not tested on Spark 4.3.
